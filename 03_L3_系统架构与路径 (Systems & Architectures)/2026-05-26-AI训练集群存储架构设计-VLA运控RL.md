# AI 训练集群存储架构设计（VLA / 运控 RL）

## 背景

自建 AI 训练集群，面向 **VLA（视觉-语言-动作模型）** 和 **运控强化学习小模型** 训练。起步阶段 10-50 卡 GPU，纯内网物理机部署，PB 级存储容量需求，研发团队兼管基础设施运维。

### 关键约束

| 维度 | 现状 |
|------|------|
| 训练类型 | VLA + 运控 RL 小模型 |
| GPU 规模 | 10-50 卡（起步），远期目标 100+ 卡 |
| 总容量 | PB 级（1-10 PB 预期） |
| 部署环境 | 纯内网物理机，自建机房 |
| 网络基础设施 | 万兆/25GbE（尚未引入 RDMA） |
| 运维能力 | 研发兼管，追求低运维复杂度 |
| 数据特征 | 视频帧较多 → 海量中小文件；checkpoint 写入频繁；RL 经验回放数据实时生成 |

## 设计原则

1. **够用优先** — 不为了"高性能"引入不必要的复杂度，10-50 卡场景下选型切合实际需求
2. **路径清晰** — 为 100+ 卡阶段留好升级路线，避免架构推倒重来
3. **协议中立** — 数据统一以 S3 对象存储为底座，不被任何协议/厂商锁定
4. **运维克制** — 以团队能接住为底线，不引入需要专人维护的组件

## 总架构

采用 **三阶段演进** 策略，从简到繁，数据底座始终是 S3 对象存储。

```
Phase 1（起步）          Phase 2（中期）          Phase 3（远期）
 0-18 个月               18-36 个月              36+ 个月
┌────────────────┐    ┌──────────────────┐    ┌──────────────────────┐
│  GPU 节点       │    │  GPU 节点         │    │  GPU 节点             │
│  ┌──────────┐   │    │  ┌────────────┐   │    │  ┌────────────────┐   │
│  │JuiceFS   │   │    │  │JuiceFS EE  │   │    │  │JuiceFS / 并行FS│   │
│  │Community │   │    │  │Kernel Client│   │    │  │混合挂载         │   │
│  └─────┬────┘   │    │  └──────┬─────┘   │    │  └───────┬────────┘   │
│        │ POSIX  │    │         │ POSIX   │    │    POSIX │   POSIX    │
└────────┼────────┘    └─────────┼─────────┘    └─────────┼─────────────┘
         │                      │                         │       │
┌────────▼────────┐    ┌────────▼─────────┐    ┌─────────▼───────▼──────┐
│  JuiceFS        │    │  JuiceFS EE      │    │  并行 FS（热数据层）    │
│  Metadata(MySQL)│    │  Metadata(EE)    │    │  3FS / BeeGFS         │
├─────────────────┤    ├──────────────────┤    │  NVMe + RDMA           │

```

## Phase 1：起步阶段 — MinIO + JuiceFS（推荐）

### 架构说明

采用 **对象存储 + FUSE POSIX** 两层架构，兼顾 S3 协议标准化和 POSIX 兼容性。

```
┌──────────────────────────────────────────────────┐
│                  GPU 训练节点 × N                   │
│  ┌──────┐ ┌──────┐ ┌──────┐                      │
│  │GPU 0 │ │GPU 1 │ │GPU 2 │ │                      │
│  │DDP/  │ │DDP/  │ │DDP/  │ │                      │
│  │FSDP  │ │FSDP  │ │FSDP  │ │                      │
│  └──┬───┘ └──┬───┘ └──┬───┘                      │
│     └───┬────┴────┬───┘                          │
│         │ POSIX /juicefs                          │
│         │ 本地缓存 SSD (可选)                      │
└─────────┼────────────────────────────────────────┘
          │ FUSE 挂载点
┌─────────▼────────────────────────────────────────┐
│              JuiceFS Gateway                       │
│  ┌─────────────────┐  ┌────────────────────────┐ │
│  │ 元数据引擎       │  │ 数据后端 (S3 API)      │ │
│  │ MySQL/Postgres  │  │ → MinIO Cluster        │ │
│  │ 主从高可用       │  │                        │ │
│  └─────────────────┘  └────────────────────────┘ │
└──────────────────────────────────────────────────┘
          │ S3 API
┌─────────▼────────────────────────────────────────┐
│              MinIO Cluster                        │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐       │
│  │ 节点 1   │  │ 节点 2   │  │ 节点 3   │       │
│  │NVMe+HDD │  │NVMe+HDD │  │HDD Only │       │
│  │(热池)    │  │(热池)    │  │(温冷池)  │       │
│  └──────────┘  └──────────┘  └──────────┘       │
│  Erasure Coding EC:4/2 or EC:6/4                 │
└──────────────────────────────────────────────────┘
```

### 关键配置

**硬件推荐：**

| 角色          | 配置                                                            | 数量    | 估算成本       |
| ----------- | ------------------------------------------------------------- | ----- | ---------- |
| MinIO 存储节点  | 双路 Xeon/EPYC, 128GB RAM, 2×3.2TB NVMe + 12×20TB HDD, 25GbE ×2 | 3-4 台 | 中等         |
| JuiceFS 元数据 | MySQL 主从（可复用现有 DB 或轻量 VM）                                     | 1-2 台 | 极低         |
| GPU 训练节点    | 本地 ≥500GB NVMe 做 JuiceFS writeback cache                      | 按需    | 已有 GPU 服务器 |

**JuiceFS 挂载参数（RL 训练优化）：**

```bash
# 针对频繁 checkpoint 写场景
juicefs mount \
  --writeback \              # 先落本地盘，异步刷 MinIO
  --cache-size=102400 \      # 本地缓存 100GB
  --buffer-size=1024 \       # 读写 buffer 1MB  
  --prefetch=8 \             # 预读并发数
  --open-cache=120 \         # 文件句柄缓存 120s
  --attr-cache=120 \         # 属性缓存 120s
  --entry-cache=120          # 目录项缓存 120s
  redis://... /juicefs
```

**元数据引擎选型：**

| 引擎 | 适合 | 风险 |
|------|------|------|
| **Redis** | 纯缓存场景，文件量 < 1 亿 | 崩溃丢元数据风险高，不推荐 |
| **MySQL/Postgres** ⭐ | **10 亿级文件量，稳定可靠** | 需要主从 HA，团队都会维护 |
| **TiKV** | 10 亿+ 文件量 | 运维负担过高，起步阶段不必要 |

> **结论：直接用 MySQL/Postgres。** VLA 训练数据解帧后文件数量快速增长，Redis 的风险不值得冒，MySQL 是成熟可靠的选择。

### VLA/RL 训练的工作负载适配

| 训练阶段 | IO 模式 | JuiceFS 表现 | 优化方向 |
|----------|---------|-------------|---------|
| 数据预处理（视频→token） | 大量顺序读，少数顺序写 | ✅ 大块读命中缓存 | 本地缓存 SSD 要大 |
| 训练数据加载 | 随机读取已处理数据 | ✅ 缓存友好 | 20-50 卡共享缓存 |
| Checkpoint 落盘 | 多进程同时写入 | ⚠️ FUSE 写延迟 ~秒级 | writeback 模式将写操作异步化 |
| RL 经验回放存储 | 少量高频写入 | ✅ 可接受 | 注意 GC 频率 |
| 模型归档 | 少量写入，极少读取 | ✅ 无压力 | — |

## Phase 2：中期升级 — JuiceFS 企业版

### 触发条件

- GPU 规模达到 **80-100 卡**
- FUSE 单客户端吞吐成为瓶颈（直观判断：nvidia-smi GPU 利用率因 IO wait 而持续低于 85%）
- 容量仍有余量，网络尚未升级 RDMA

### 升级内容

| 当前（社区版） | 升级到（企业版） | 预期提升 |
|--------------|----------------|---------|
| FUSE 用户态客户端 | **Kernel 客户端**（内核态驱动） | 消除 10-30% 性能开销 |
| MySQL 元数据引擎 | 企业版自研引擎 | 10x 元数据吞吐 |
| 单机本地缓存 | 分布式缓存池 | 多节点共享热数据 |
| 社区支持 | 商业技术支持 | — |

### 迁移成本

**极低。** 数据不动、架构不变、仅替换 JuiceFS 客户端。支持灰度切换（部分节点先上线企业版）。

## Phase 3：远期 — 引入并行 FS 作为热数据层

### 触发条件

- GPU 规模达到 **200+ 卡**
- Checkpoint 写入延迟成 GPU 利用率瓶颈（checkpoint 耗时 > 5s，导致多卡 idle）
- 网络已升级到 **RoCE v2 或 InfiniBand**（必要条件）

### 分层架构

引入并行 FS 不替代 MinIO，而是作为热数据层，与 MinIO 共存：

```
GPU 训练节点
  ┌─────────────────────────────┐
  │ /fast/     →  并行 FS       │  ← RDMA 直连
  │ 活跃训练集、checkpoint      │     亚毫秒延迟
  ├─────────────────────────────┤
  │ /archive/  →  MinIO+JuiceFS │  ← 25GbE
  │ 原始视频、历史数据、模型归档   │    秒级延迟可接受
  └─────────────────────────────┘
```

### 并行 FS 选型

| 方案 | RDMA 要求 | 运维复杂度 | AI 场景验证 | 推荐时机 |
|------|----------|-----------|------------|---------|
| **3FS** | 必需 | 高 | DeepSeek 验证，社区尚小 | 团队有 Infra 经验 + 愿意拥抱开源 |
| **BeeGFS** | 可选（非 RDMA 也能跑） | 中等 | HPC 成熟，AI 场景已验证 | 较早升级路径，网络未升级 RDMA 时 |
| **WekaFS** | 推荐 | 低（商业支持） | Weka 在 AI 存储标杆地位 | 预算充足，GPU idle 成本高 |
| **Lustre** | 推荐 | 高 | HPC 黄金标准，AI 已验证 | 团队有 HPC 背景 |

> **当前阶段的建议：暂不深入选择。** Phase 3 至少是 18 个月后的事，届时硬件方案和开源社区都会进化。现在只需为 RDMA 留好网络升级空间。

## 网络规划（最关键的提前决策）

网络是决定存储架构可升级性的 **唯一不可逆基础设施决策**。布线换不了，交换机升级贵。

### 起步阶段（Phase 1）网络拓扑

```
                ┌──────────────┐
                │ Spine 交换机  │ 25GbE/100GbE
                └──────┬───────┘
          ┌────────────┼────────────┐
          │            │            │
    ┌─────▼────┐ ┌─────▼────┐ ┌─────▼────┐
    │GPU 节点 1 │ │GPU 节点 2 │ │    ...    │
    │25GbE×2   │ │25GbE×2   │ │          │
    └──────────┘ └──────────┘ └──────────┘
          │            │
    ┌─────▼────────────▼─────┐
    │ 存储 Leaf 交换机        │
    │ 25GbE (支持 RoCE)      │
    └─────┬────────────┬─────┘
          │            │
    ┌─────▼────┐ ┌─────▼────┐
    │MinIO 节点│ │MinIO 节点│
    │25GbE×2   │ │25GbE×2   │
    └──────────┘ └──────────┘
```

### 关键要求

1. **交换机选型：选择支持 RoCE v2 的型号**（大部分 25GbE+ 交换机都支持 PFC + ECN），即使起步阶段不启用 RDMA，也要支持配置
2. **布线预埋：存储节点到 GPU 节点之间留好光缆/铜缆**，未来升级 RoCE 时无需重新布线
3. **存储节点双网卡：25GbE ×2**，bonding 提供冗余 + 带宽叠加
4. **GPU 节点：如果预算允许，用 100GbE 连接 GPU 节点**，向下兼容 25GbE，未来 upgrade 时减少交换机更换

## 关键选型决策记录

### 为什么不直接从 SeaweedFS 起步

SeaweedFS 的技术栈非常精简（Go 二进制，单系统部署），对研发兼管团队有吸引力。但在本场景中有两个顾虑：

1. **Checkpoint 覆写兼容性**：SeaweedFS 底层是 append-only 模型，而 RL 训练中 checkpoint 路径通常固定（每次写同路径）。这会持续产生垃圾版本，需额外设计 GC 策略（写时间戳路径 + symlink 指向最新版）。**这在技术上可解决，但增加了训练脚本的心智负担。**

2. **AI 训练场景验证度不足**：SeaweedFS 核心场景是海量小文件对象存储，在 AI 训练（大规模 POSIX checkpoint 写入）方面的公开案例和最佳实践较少。作为起步阶段的存储底座，选验证更充分的方案更稳妥。

**SeaweedFS 的合理位置：** 如果团队倾向于纯对象存储场景（数据预处理管线全部走 S3 API），SeaweedFS 是 MinIO 的轻量替代品。但对本场景需要的 POSIX checkpoint 写入，不算最优选择。

### 为什么不直接在 Phase 1 用 BeeGFS

BeeGFS 是 HPC 和 AI 训练中验证充分的并行文件系统。但本场景中：
- 10-50 卡规模下，BeeGFS 的性能优势无法充分发挥
- 运维成本是实打实的（内核模块版本管理、客户端更新、LACP 配置）
- 团队研发兼管，并行 FS 的日常维护缺乏专项人力

**BeeGFS 的合理位置：** Phase 3 的热数据层候选方案之一。

### 为什么元数据引擎选 MySQL 而非 Redis

Redis 作为 JuiceFS 元数据引擎只在文件量 < 1 亿、可接受元数据丢失的场景下推荐。VLA 视频解帧后文件数量可快速达到千万级，且元数据丢失后整个文件系统不可用。MySQL/Postgres 成熟稳定，团队普遍有运维经验，是本场景的正确选择。

## 迁移路径总结

```
时间线        规模         存储方案                        网络
──────────────────────────────────────────────────────────────────
Phase 1    10-50 卡     MinIO(3-4节点) + JuiceFS(MySQL)    25GbE
  (0-18月)             NVMe 热 + HDD 温冷                 预留 RoCE 能力

Phase 2    80-100 卡    JuiceFS 企业版 (Kernel Client)      25GbE / 局部 100GbE
  (18-36月)            数据不动，提升性能                    评估 RDMA 升级

Phase 3    200+ 卡      并行 FS 热数据层 (3FS/BeeGFS)      RoCE v2 / InfiniBand
  (36月+)              + MinIO 温冷归档                    存储和计算网络分离
```
