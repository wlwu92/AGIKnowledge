# ansible/ansible — 自动化运维平台

> Red Hat 赞助的开源 IT 自动化平台，通过 SSH 实现无代理（agentless）的配置管理、应用部署和任务编排。

## 用途

以人类可读的 Playbook（YAML）描述基础设施期望状态，通过 SSH 对远程机器批量执行任务。替代手动运维，将基础设施配置版本化、可审计、可复现。

## 核心能力

- **无代理架构**：通过 SSH 连接远程节点，无需安装任何 agent 或额外守护进程
- **人类可读**：Playbook 使用 YAML 描述，接近自然语言，学习曲线低
- **并行执行**：默认并行管理多台机器
- **模块化设计**：模块可用 Python 及任何动态语言开发
- **幂等性**：同一 Playbook 反复执行，结果一致
- **生态丰富**：内置数千个模块覆盖系统、网络、云、容器、安全等领域

## 典型场景详解

以下四个场景覆盖了 Ansible 最常用的模式：**机器级配置管理**、**开发环境管理**、**容器化部署**、以及 **Packer + Ansible 分工配合**。前三个场景假设没有 Packer（裸机或小规模集群），第四个展示两者如何协作。

### 场景一：GPU 集群节点初始化（纯 Ansible 模式）

> ⚠️ **适用条件**：本场景假设没有 Packer 参与——也就是裸机部署、或只需要管理少量长生命周期节点。如果用了 Packer 构建 AMI（见场景四），这里的 NVIDIA 驱动和 Docker 就不需要 Ansible 做了。

新建一台 GPU 服务器，从裸机到可跑分布式训练的全部步骤。其中用注释标注了 ⚡ 的任务意味着**如果用了 Packer，这些应该搬到 AMI 里**：

```yaml
# plays/gpu-node-init.yml
---
- name: GPU 节点初始化
  hosts: gpu_nodes
  become: true
  vars:
    nvidia_driver_version: "550"
    docker_version: "24.0"
    nccl_debug: "WARN"
    shared_storage: "/mnt/efs"

  tasks:
    # ═══════════════════════════════════════════════
    # ⚡ Packer 领地：安装频率低 + 需要重启
    #   如果已有 Packer AMI，这些任务全部跳过
    # ═══════════════════════════════════════════════
    - name: 安装 NVIDIA 驱动
      apt:
        name:
          - nvidia-driver-{{ nvidia_driver_version }}
          - nvidia-utils-{{ nvidia_driver_version }}
        state: present
        update_cache: true
      register: nvidia_install
      notify: reboot host

    - name: 安装 Docker
      apt:
        name:
          - docker.io
          - docker-compose-v2
        state: present

    - name: 安装 NVIDIA Container Toolkit
      apt:
        name: nvidia-container-toolkit
        state: present

    - name: 配置 Docker daemon（GPU runtime）
      template:
        src: templates/daemon.json.j2
        dest: /etc/docker/daemon.json
      notify: restart docker

    # ═══════════════════════════════════════════════
    # ✅ Ansible 领地：实例特有、频繁变化、依赖运行时信息
    # ═══════════════════════════════════════════════
    - name: 挂载共享存储（EFS）
      mount:
        src: "{{ efs_dns }}:/"
        path: "{{ shared_storage }}"
        fstype: nfs4
        opts: "nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2"
        state: mounted

    - name: 创建训练用户
      user:
        name: "{{ item }}"
        groups: docker
        shell: /bin/bash
      loop: "{{ training_users }}"

    - name: 写入分布式训练 SSH 配置
      template:
        src: templates/ssh_config.j2
        dest: /home/{{ item }}/.ssh/config
        owner: "{{ item }}"
        mode: '0600'
      loop: "{{ training_users }}"

    - name: 配置 NCCL 环境变量
      lineinfile:
        path: /etc/environment
        regexp: "^{{ item.key }}="
        line: "{{ item.key }}={{ item.value }}"
      loop:
        - { key: NCCL_DEBUG, value: "{{ nccl_debug }}" }
        - { key: NCCL_IB_DISABLE, value: "0" }
        - { key: NCCL_NET_GDR_LEVEL, value: "5" }

  handlers:
    - name: restart docker
      systemd:
        name: docker
        state: restarted
        daemon_reload: true

    - name: reboot host
      reboot:
        reboot_timeout: 300
```

配套模板 `daemon.json.j2`：

```jinja2
{
  "default-runtime": "nvidia",
  "runtimes": {
    "nvidia": {
      "path": "nvidia-container-runtime",
      "runtimeArgs": []
    }
  },
  "storage-driver": "overlay2",
  "exec-opts": ["native.cgroupdriver=systemd"],
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "100m",
    "max-file": "3"
  },
  "features": {
    "buildkit": true
  }
}
```

执行：

```bash
ansible-playbook -i inventory/gpu-cluster.yml plays/gpu-node-init.yml \
  --limit gpu-0[1:4]       # 只对 gpu-01 到 gpu-04 执行
```

### 场景二：开发机环境配置（macOS / Linux）

> ⚠️ **跟服务器的本质区别**：开发机是给人用的，不是给机器用的。个人偏好（用什么编辑器、Prompt 长什么样、Dock 放哪边）**不应被中央管理**。公司需要用 Ansible 管的，仅限于"跟协作和合规相关"的部分。

#### 从公司视角：什么才是真正需要管的

#### 开发机管理清单（重分类版）

| 策略        | 管理域           | 具体内容                                         | 变更频率       |
| --------- | ------------- | -------------------------------------------- | ---------- |
| **🔒 强制** | 安全基线          | 屏幕锁策略（60s 自动锁）、FileVault、防火墙                 | 一次性 + 合规抽查 |
| **🔒 强制** | SSH + GPG 密钥  | 注入公司 SSH 密钥、配置 GPG 签名 key、ssh_config 模板      | 偶尔（人员变动）   |
| **🔒 强制** | Git 合规        | `commit.gpgSign=true`、commit 模板、全局 gitignore | 一次性        |
| **🔒 强制** | 网络访问          | VPN 配置、内部 registry 证书、代理设置                   | 偶尔（IT 变更）  |
| **📋 推荐** | 语言运行时         | Python 3.12（pyenv）、Node 22（nvm）、Go 1.23      | 月级（版本升级）   |
| **📋 推荐** | 容器/云工具        | Docker、kubectl、helm、terraform、aws-cli        | 月级         |
| **📋 推荐** | 基础 CLI 工具     | git、curl、jq、ripgrep、htop、tmux                | 季度         |
| **📋 推荐** | VS Code 基线    | 推荐扩展列表 + `.editorconfig`                     | 偶尔         |
| **📋 推荐** | dotfiles      | 提供一个可选模板，不强制使用                               | 偶尔         |
| **🎁 可选** | Shell 增强      | zsh 插件、starship prompt、fzf、bat、lazygit       | —          |
| **🎁 可选** | macOS 便利      | Dock/Finder 设置、截图目录、键盘加速                     | —          |
| **🎁 可选** | VS Code 主题/字体 | 编辑器皮肤、编程字体                                   | —          |

#### 分层管理：三份 playbook，按需执行

把"哪些该管"的思考结果映射到文件结构——不是一份大而全的 playbook，而是三份职责明确的 playbook：

```
playbooks/
├── workstation-mandatory.yml    # 🔒 强制 — 安全基线 + 合规配置
├── workstation-recommended.yml  # 📋 推荐 — 工具链 + 运行时
└── workstation-optional.yml     # 🎁 可选 — Shell 主题 + 系统偏好
```

三层之间的依赖关系：推荐层依赖强制层（合规先到位），可选层完全独立（爱跑不跑）。

##### 🔒 workstation-mandatory.yml — 安全与合规基线

```yaml
# plays/workstation-mandatory.yml
---
- name: 安全与合规基线
  hosts: localhost
  connection: local
  gather_facts: true

  vars:
    # Git 身份信息 — 来自环境变量（HR 入职流程中设置）
    git_user_name: "{{ lookup('env', 'GIT_USER_NAME') }}"
    git_user_email: "{{ lookup('env', 'GIT_USER_EMAIL') }}"

  tasks:
    # ── SSH ──
    - name: 确保 ~/.ssh 存在
      file:
        path: ~/.ssh
        state: directory
        mode: '0700'

    - name: 注入公司 SSH 密钥
      copy:
        content: "{{ vault_ssh_key }}"
        dest: ~/.ssh/id_ed25519
        mode: '0600'

    - name: 写入 SSH 配置（跳板机、内部仓库）
      template:
        src: templates/ssh_config.j2
        dest: ~/.ssh/config
        mode: '0600'

    # ── GPG + Git 合规 ──
    - name: 导入 GPG 签名密钥
      copy:
        content: "{{ vault_gpg_key }}"
        dest: /tmp/gpg-key.asc
      changed_when: false

    - name: 配置 Git 身份（强制 — 影响代码追溯）
      git_config:
        name: "{{ item.name }}"
        scope: global
        value: "{{ item.value }}"
      loop:
        - { name: user.name, value: "{{ git_user_name }}" }
        - { name: user.email, value: "{{ git_user_email }}" }
        - { name: commit.gpgSign, value: "true" }
        - { name: init.defaultBranch, value: main }
        - { name: pull.ff, value: only }

    - name: 写入全局 gitignore（公司级忽略规则）
      copy:
        dest: ~/.gitignore_global
        content: |
          .DS_Store
          .idea/
          *.swp
          .env
          .venv/
          __pycache__/
      register: gitignore
      notify: reconfigure git

    # ── 安全基线 ──
    - name: 检查 FileVault 状态（macOS）
      command: fdesetup status
      when: ansible_os_family == "Darwin"
      register: fv_status
      failed_when: "'FileVault is Off' in fv_status.stdout"
      changed_when: false

    - name: 启用屏幕锁（macOS）
      community.general.osx_defaults:
        domain: com.apple.screensaver
        key: askForPassword
        type: int
        value: 1
      when: ansible_os_family == "Darwin"

    # ── 内部网络 ──
    - name: 信任公司内部 CA 证书
      copy:
        src: "files/internal-ca.crt"
        dest: /usr/local/share/ca-certificates/internal-ca.crt
      when: ansible_os_family == "Debian"

  handlers:
    - name: reconfigure git
      shell: git config --global core.excludesfile ~/.gitignore_global
```

> **为什么 Git 身份（name/email）是"强制"？**
> 代码提交的身份信息关联到 code review 追责、DCO 合规、安全审计。用错了名字意味着 commit 无法追溯回真实作者——这不是个人偏好，是合规要求。实践中 `GIT_USER_NAME` 和 `GIT_USER_EMAIL` 由 HR onboarding 脚本设置，开发者在入职当天就知道自己的公司 Git 身份。

##### 📋 workstation-recommended.yml — 工具链与运行时

```yaml
# plays/workstation-recommended.yml
---
- name: 推荐工具链
  hosts: localhost
  connection: local
  gather_facts: true

  vars_files:
    - vars/packages.yml          # 包清单（分组管理）

  tasks:
    # ── 系统依赖 ──
    - name: 安装 Xcode CLI Tools（macOS）
      command: xcode-select --install
      when: ansible_os_family == "Darwin"
      changed_when: false
      failed_when: false

    - name: 安装 Homebrew（macOS）
      shell: |
        /bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
      when: ansible_os_family == "Darwin"
      changed_when: false

    - name: Linux 基础包
      package:
        name: "{{ base_packages }}"
        state: present
      when: ansible_os_family == "Debian"

    # ── Homebrew 包 ──
    - name: 安装推荐工具（macOS）
      homebrew:
        name: "{{ item }}"
        state: present
      loop: "{{ brew_recommended }}"
      when: ansible_os_family == "Darwin"

    - name: 安装开发语言工具（macOS）
      homebrew:
        name: "{{ item }}"
        state: present
      loop: "{{ brew_languages }}"
      when: ansible_os_family == "Darwin"

    - name: 安装云工具（macOS）
      homebrew:
        name: "{{ item }}"
        state: present
      loop: "{{ brew_cloud }}"
      when: ansible_os_family == "Darwin"

    # ── 语言运行时 ──
    - name: 安装 pyenv（Python 版本管理）
      shell: curl -fsSL https://pyenv.run | bash
      changed_when: false

    - name: 安装推荐 Python 版本
      shell: |
        pyenv install {{ python_recommended }} --skip-existing
        pyenv global {{ python_recommended }}
      changed_when: false

    - name: 安装 nvm + Node.js
      shell: |
        curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.0/install.sh | bash
        nvm install {{ node_recommended }}
      changed_when: false

    # ── VS Code 扩展 ──
    - name: 安装推荐 VS Code 扩展
      command: "code --install-extension {{ item }}"
      loop: "{{ vscode_extensions }}"
      changed_when: false
      failed_when: false

    - name: 写入 .editorconfig（团队统一）
      copy:
        dest: ~/.editorconfig
        content: |
          root = true

          [*]
          charset = utf-8
          end_of_line = lf
          indent_style = space
          indent_size = 2
          trim_trailing_whitespace = true
          insert_final_newline = true

          [*.py]
          indent_size = 4

          [*.md]
          trim_trailing_whitespace = false
```

#### 为什么这么分

| 层 | 管什么 | 不管什么 | 理由 |
|----|--------|---------|------|
| **🔒 强制** | SSH 密钥、GPG 签名、Git 身份、FileVault、防火墙、内部 CA | 编辑器主题、字体、Prompt | 这些出问题直接影响安全和合规——密钥泄露、commit 不可追溯、设备未加密。而 Prompt 好不好看跟公司无关 |
| **📋 推荐** | 语言运行时版本、CLI 工具、VS Code 扩展、`.editorconfig` | 不限制开发者装其他工具、不禁止用 IntelliJ 替代 VS Code | 版本一致性减少"在我的机器上能跑"问题。但禁止用其他编辑器 = 过度管理 |
| **🎁 可选** | Shell 插件、Dock 设置、Finder 设置 | 不主动推送，不做默认配置 | 属于个人生产力优化的东西，公司不创造价值也不承担风险。提供 playbook 给有需要的人自取 |

**核心判断标准**：这个配置如果没统一管理，公司是否会产生成本或风险？
- 是 → 🔒 强制 或 📋 推荐
- 否 → 🎁 可选 或 不管

#### 执行方式

```bash
# 新员工入职：三步跑完
ansible-playbook plays/workstation-mandatory.yml --ask-vault-pass   # 安全 + 合规
ansible-playbook plays/workstation-recommended.yml                  # 工具链
ansible-playbook plays/workstation-optional.yml                     # 可选（新人自选）

# 按需更新（只跑某一层）
ansible-playbook plays/workstation-recommended.yml --tags vscode    # 仅更新 VS Code 扩展

# ansible-pull 推荐用于定期同步强制层
# 配合 launchd 或 cron 每小时自动检查
ansible-pull -U https://github.com/team/dev-env.git   -i localhost,   plays/workstation-mandatory.yml   --accept-host-key
```

**实践建议**：`workstation-mandatory.yml` 通过 ansible-pull 定期执行（确保安全基线不漂移），`workstation-recommended.yml` 随团队节奏手动触发（版本升级时），`workstation-optional.yml` 开发者自选执行，不纳入 CI/CD。

#### 开发机 vs 服务器的 Ansible 使用差异

| 维度 | 服务器 | 开发机 |
|------|--------|--------|
| 连接方式 | `connection: ssh` | `connection: local` |
| 执行触发 | CI/CD 或手动推送 | `ansible-pull` 定时拉取（强制层）+ 按需手动（推荐层） |
| 幂等性要求 | 严格（不能重启生产服务） | 宽松（开发机重启不影响他人） |
| 变量来源 | group_vars + vault | 环境变量（`lookup('env')`）+ vault（密钥） |
| 配置分层 | 通常一份 playbook 完成 | 三层分离（强制/推荐/可选），按需执行 |
| 个人偏好 | 不存在（机器没有"喜好"） | 明确不管理——只管理"跟协作和合规相关"的配置 |
| 最大风险 | 误配置导致服务中断 | 误配置影响个人效率，不影响团队 |

#### 新员工入职流程：从开箱到跑起来

> ⚠️ **先有鸡还是先有蛋？** 新 MacBook 没有 `git`，没有 SSH 密钥，但需要这些才能 clone 仓库、跑 playbook。这个悖论需要**分两步解决**：先用 `curl`（macOS 自带）拿到 playbook，跑完强制层配好 SSH，之后才能正常使用 `git`。

##### 方案选择

| 方案 | 做法 | 适用条件 | 评价 |
|------|------|---------|------|
| **A. curl 下载 ZIP** | 浏览器或 curl 下载 dev-env 仓库 ZIP，解压后直接跑 | 任何公司 | 最通用，不依赖任何前置工具 |
| **B. IT 预装** | IT 部门在发机前装好 Xcode CLI Tools + 克隆 dev-env | 有 IT 预装流程的公司 | 体验最好，新员工开箱即用 |
| **C. bootstrap 脚本** | 公司维护一个 `bootstrap.sh`，一条命令完成所有前置 | 有内部 CDN 或文件服务器的公司 | 最简，但需要额外维护 |

### 场景三：容器化应用滚动部署

场景：部署/更新一个 PyTorch 推理服务，分批次更新，失败自动回滚：

```yaml
# plays/deploy-inference.yml
---
- name: 滚动部署推理服务
  hosts: inference_nodes
  serial: 1            # ← 一次只更新一台，用于验证
  max_fail_percentage: 25   # 超过 25% 失败则中止

  vars:
    image: "{{ registry }}/inference-server:{{ image_tag | default('latest') }}"
    container_name: inference
    health_url: "http://localhost:8080/health"

  tasks:
    - name: 将当前节点从负载均衡移除
      command: "aws elbv2 deregister-targets ..."
      delegate_to: localhost
      when: elb_enabled | default(false)

    - name: 拉取新版本镜像
      docker_image:
        name: "{{ image }}"
        source: pull

    - name: 停止旧容器
      docker_container:
        name: "{{ container_name }}"
        state: absent

    - name: 启动新容器
      docker_container:
        name: "{{ container_name }}"
        image: "{{ image }}"
        state: started
        restart_policy: always
        ports:
          - "8080:8080"
        env:
          MODEL_PATH: "{{ model_path }}"
          BATCH_SIZE: "{{ batch_size | default(32) }}"
          CUDA_VISIBLE_DEVICES: "0,1"
        volumes:
          - "{{ model_path }}:/models:ro"
          - "/dev/shm:/dev/shm"
        networks:
          - name: app_network
        healthcheck:
          test: ["CMD", "curl", "-f", "{{ health_url }}"]
          interval: 10s
          timeout: 5s
          retries: 3

    - name: 等待健康检查通过
      uri:
        url: "{{ health_url }}"
        method: GET
      register: health
      until: health.status == 200
      retries: 30
      delay: 2

    - name: 注册回负载均衡
      command: "aws elbv2 register-targets ..."
      delegate_to: localhost
      when: elb_enabled | default(false)

    - name: 记录部署版本
      local_action:
        module: copy
        content: "{{ image_tag }}"
        dest: "./deploy-log/{{ inventory_hostname }}.version"
```

### 场景四：Packer + Ansible 分工实战

混合模式：Packer 构建 GPU AMI，Ansible 做云上实例的最终配置。

**Step 1 — Packer 构建黄金 AMI（HCL 定义）**

```hcl
# gpu-ami.pkr.hcl
source "amazon-ebs" "gpu" {
  ami_name      = "gpu-base-{{ isotime | clean_ami_name }}"
  instance_type = "p4d.24xlarge"
  region        = "us-west-2"

  # 基础镜像：Ubuntu 22.04 最小化
  source_ami_filter {
    filters = {
      name                = "ubuntu/images/*ubuntu-jammy-22.04-amd64-server-*"
      root-device-type    = "ebs"
      virtualization-type = "hvm"
    }
    most_recent = true
    owners      = ["099720109477"]
  }

  ssh_username = "ubuntu"
}

build {
  sources = ["source.amazon-ebs.gpu"]

  # ← 这里用 Ansible 作为 Packer 的 provisioner！
  #   同一个 playbook 既可用于 Packer 构建 AMI，
  #   也可用于后续对运行中实例做配置修正
  provisioner "ansible" {
    playbook_file = "./plays/ami-provision.yml"
    extra_arguments = [
      "--extra-vars", "build_mode=ami"
    ]
  }
}
```

**关键设计**：Packer 的 provisioner 可以直接用 Ansible，所以**同一个 playbook 可以被两种消费**：
- 在 Packer 构建 AMI 时执行（`build_mode=ami`）→ 写入慢变层
- 实例运行后 Ansible 单独执行（`build_mode=live`）→ 只做快变层的修正

**Step 2 — 同一套 playbook 用于 AMI 构建和运行时配置**

```yaml
# plays/ami-provision.yml
---
- name: 构建黄金 AMI / 修正运行实例
  hosts: all
  become: true
  vars:
    build_mode: "{{ build_mode | default('live') }}"

  tasks:
    # ═══════════════════════════════════
    # 慢变层：只在 AMI 构建时安装
    # ═══════════════════════════════════
    - block:
        - name: 安装 NVIDIA 驱动
          apt:
            name: nvidia-driver-550
            state: present

        - name: 安装 Docker + Container Toolkit
          apt:
            name:
              - docker.io
              - nvidia-container-toolkit
            state: present

        - name: 写入 Docker daemon.json
          copy:
            src: files/daemon.json
            dest: /etc/docker/daemon.json

        - name: 安装监控 agent
          apt:
            name: cloudwatch-agent
            state: present
      when: build_mode == "ami"    # ← 只有 Packer 构建时执行

    # ═══════════════════════════════
    # 快变层：每次都执行（幂等）
    # ═══════════════════════════════
    - name: 确保 Docker 运行
      service:
        name: docker
        state: started
        enabled: true

    - name: 确保监控 agent 运行
      service:
        name: amazon-cloudwatch-agent
        state: started
        enabled: true
```

**Step 3 — Terraform 用 Packer AMI 启动实例**

```hcl
# main.tf
resource "aws_launch_template" "gpu" {
  name          = "gpu-cluster"
  image_id      = data.aws_ami.gpu_base.id      # ← Packer 构建的 AMI
  instance_type = "p4d.24xlarge"

  user_data = base64encode(templatefile("userdata.sh", {
    efs_dns      = aws_efs_file_system.data.dns_name
    cluster_name = var.cluster_name
  }))
}

resource "aws_autoscaling_group" "gpu" {
  launch_template {
    id      = aws_launch_template.gpu
    version = "$Latest"
  }
  min_size = 1
  max_size = 10
  # ...
}
```

**Step 4 — 实例启动后，Ansible 做最终配置**

实例启动时通过 `user_data` 做最小化自举：

```bash
# userdata.sh：实例启动时自动执行
#!/bin/bash
# 注册到 Ansible 控制节点
aws ec2 create-tags --resources $(curl -s http://169.254.169.254/latest/meta-data/instance-id) \
  --tags Key=ansible_managed,Value=true

# 触发 Ansible pull 做最终配置
ansible-pull -U https://github.com/team/cluster-config.git \
  plays/gpu-live.yml \
  --accept-host-key
```

### Packer 可以被 Ansible 替代吗？

**功能上有重叠，但架构理念不同，不是简单的替代关系。**

#### 什么时候 Ansible 就够了

| 条件 | 说明 | 举例 |
|------|------|------|
| 机器数量少 | 个位数节点，逐个管理成本可接受 | 实验室 4 台 GPU 工作站 |
| 长生命周期 | 机器跑几个月甚至几年，不频繁销毁重建 | 内网开发服务器 |
| 裸机/无虚拟化 | 物理机，没有 AMI 的概念 | 办公室 Linux 台式机 |
| 配置变化频繁 | 每周调整软件版本和环境参数 | 算法团队的研究环境 |

这些场景下，Ansible 从零配置一台机器完全可行，Packer 带来的额外复杂度不划算。

#### 什么时候必须用 Packer

| 条件 | 为什么 Packer 不可替代 |
|------|----------------------|
| **规模启动** | 100 台 GPU 实例同时启动，每台等 Ansible 跑 15 分钟配置 = 不可接受。Packer AMI 启动即就绪 |
| **弹性伸缩/竞价实例** | 实例随时可能被回收重建，每次都要等 Ansible 配置完才能干活？Packer AMI 秒级就绪 |
| **不可变基础设施** | 合规要求"线上实例不能手工修改，变更必须走镜像版本"。Ansible 的在线修正恰好是违规行为 |
| **多平台构建** | 同一份定义产出 AMI + Vagrant box + ISO，Ansible 做不到 |
| **隔离构建** | Packer 在纯净的构建环境中执行，控制节点的状态不会污染镜像 |

#### 最实用的判断方式

```
你的场景：
  1. 实例启动后等待几分钟才能干活 → 能接受 → Ansible 够了
                                   → 不能接受 → 需要 Packer

  2. 实例是否频繁销毁重建 → 是 → Packer AMI
                          → 否 → Ansible 够用

  3. 是否只有一种部署平台 → 是 → Ansible 够用（但 Packer 也可以）
                          → 否（AWS + 本地 Vagrant）→ Packer 更省事
```

**实践中最常见的模式**是混合：Packer 只做 AMI（把最耗时的驱动安装固化进去），Ansible 做剩下的全部（挂载存储、注入配置、管理用户、部署应用）。[[2026-05-19-IaC基础设施即代码工具链|IaC 工具链综述]] 中有更完整的对比。

## 适用边界

- **优势场景**：配置管理、应用部署、多云编排、零停机滚动更新
- **不适用于**：实时监控（非事件驱动）、需长期驻留 agent 的场景（检查频率低，不适合秒级响应）
- **对比容器方案**：Ansible 管理的是**机器/VM 级别的配置**，Docker/K8s 管理的是**容器级别**
- **在 IaC 工具链中的位置**：Ansible 负责配置管理阶段，与 Terraform（资源编排）和 Packer（镜像构建）互补串联，见 [[2026-05-19-IaC基础设施即代码工具链|IaC 工具链综述]]
- AI Infra 中适用于：批量部署 GPU 驱动/CUDA 环境、管理实验集群节点、搭建分布式训练基础设施

## 快变层管理实战

在 IaC 体系中 Ansible 负责"快变层"——那些频繁变化、不适合固化到 Packer 机器镜像中的运维操作。以下逐一拆解。

### 秘钥注入

密钥管理的核心矛盾：**代码要版本化，密钥不能进仓库**。Ansible 提供三层递进方案：

#### 方案一：Ansible Vault（内置加密）

最轻量，适合小团队或单个项目。下面从创建到使用拆解完整流程。

##### 创建加密变量文件

```bash
# 交互式：创建并编辑（会提示设置密码）
ansible-vault create vars/secrets.yml

# 非交互：从明文文件加密（适合 CI/CD 中从 secrets 导出）
ansible-vault encrypt --output vars/secrets.yml vars/secrets_plain.yml
rm vars/secrets_plain.yml   # 立即删除明文
```

加密后的内容是一段 AES256 密文，以 YAML 格式存储：

```yaml
# vars/secrets.yml（cat 看到的原始内容）
db_password: !vault |
  $ANSIBLE_VAULT;1.1;AES256
  66386439653236336...6138386136663530
  323162653434353031...3763643233306563
  35616238343834623...36336333373162
slack_webhook: !vault |
  $ANSIBLE_VAULT;1.1;AES256
  35616238343834623...36336333373162
  62353531323737363...39646134666435
  35306362353738376...32333730363539
```

每个 `!vault` 块是独立加密的。文件仍然是合法的 YAML，key 结构是明文的，只有 value 被加密。

##### 如何在 playbook 中引用

加密变量文件通过 `vars_files` 或 `include_vars` 加载，Ansible 在执行时自动解密：

```yaml
# deploy.yml
---
- name: 部署应用
  hosts: web_servers
  vars_files:
    - vars/secrets.yml          # ← 加载加密文件，解密后 merge 到变量空间
    - vars/app_config.yml       # ← 明文配置，变量名不冲突即可
  tasks:
    - name: 配置数据库连接
      template:
        src: app.conf.j2
        dest: /etc/myapp/config.conf
      # 模板中可以直接使用 {{ db_password }}，Ansible 已自动解密
```

或根据环境动态加载：

```yaml
- name: 按环境加载对应密钥
  include_vars: "vars/{{ env }}/secrets.yml"
  no_log: true
```

模板中使用时完全无感：

```jinja2
{# app.conf.j2 #}
[Database]
host = {{ db_host }}
port = {{ db_port | default(5432) }}
password = {{ db_password }}    {# ← 变量来自加密文件，Ansible 已解密为明文 #}
user = {{ db_user }}
```

##### 如何指定 vault 密码执行

`ansible-vault` 加密时设置的密码，在执行时通过以下方式传入，**不会落盘**：

```bash
# 方式A：手动输入（适合开发机调试）
ansible-playbook deploy.yml --ask-vault-pass

# 方式B：从文件读取（适合 CI/CD，文件本身由 secrets 管理）
ansible-playbook deploy.yml --vault-password-file .vault_pass

# 方式C：Vault ID 多环境隔离
ansible-playbook deploy.yml \
  --vault-id prod@.vault_pass_prod \
  --vault-id staging@.vault_pass_staging
```

**`.vault_pass` 这个文件本身绝对不能进仓库！** 它的内容就是一行密码字符串。在 CI/CD 中，这个文件由管道平台的 Secrets 功能在运行时写入：

```yaml
# .github/workflows/deploy.yml
- name: 写入 vault 密码并执行
  run: |
    echo "${{ secrets.VAULT_PASSWORD }}" > .vault_pass
    ansible-playbook deploy.yml --vault-password-file .vault_pass
  shell: bash
```

💡 **存放位置推荐**：`.vault_pass` 的内容通常保存在 **GitHub Environments** 的 secrets 中（`Settings → Environments → <env-name> → Environment secrets`）。每个环境（`prod`/`staging`/`dev`）有独立的 vault 密码，互不可见，workflow 通过 `environment:` 字段指定使用哪个：

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: prod       # ← 只有此 job 有权读取 prod 的 secrets
    steps:
      - run: |
          echo "${{ secrets.VAULT_PASSWORD }}" > .vault_pass
          ansible-playbook deploy.yml --vault-password-file .vault_pass \
            -e env=prod
```

用 GitHub Environments 的好处：
- **环境隔离**：prod/staging/dev 各一个 vault 密码，泄露一个不影响其他
- **审批门禁**：prod 环境可设置"必须有人审批才能执行"
- **审计追踪**：谁在什么时候触发了部署，有完整记录

##### 为什么加密后进仓库是安全的

理解这个问题要分清两个"密钥"：

| 密钥 | 位置 | 作用 |
|------|------|------|
| **Vault 密码**（Vault Password） | 不进仓库，保存在 CI/CD Secrets / 密码管理器 | 用于加密和解密，是唯一需要保护的东西 |
| **Vault 加密文件**（Encrypted File） | **进仓库** | 内容是 AES256 密文，没有 Vault 密码就是乱码 |

所以加密文件的"安全性"来自两个事实：

**① AES256 加密强度**：Ansible Vault 使用 AES-CTR-256 加密 + HMAC-SHA256 完整性校验。现代计算能力下暴力破解 AES256 密钥空间（2²⁵⁶）在可预见的未来不现实。也就是说，**攻击者拿到了加密文件，没有密码也解不开**。

**② 威胁模型是"仓库泄露而非算法破解"**。主要防护场景：

| 威胁 | 加密文件暴露 | Vault 密码位置 | 风险 |
|------|------------|--------------|------|
| 仓库被公开/泄露 | ✔️ 文件在其中 | 在 CI/CD Secrets 中，不受影响 | 安全 |
| 内鬼有仓库只读权限 | ✔️ 能读到密文 | 无 vault 密码 | 安全 |
| CI/CD 管道日志泄露 | task 上加了 `no_log: true` | 密码通过 `${{ secrets }}` 传入，不会显示 | 安全（取决于 CI 平台） |
| CI/CD Secrets 泄露 | — | 密码暴露 | ❌ 全量泄露 |

**唯一真正的风险点**是 vault 密码本身的管理。密码要：
- 高熵（不短于 32 位，大小写 + 数字 + 符号）
- 存在密码管理器中（1Password/Bitwarden），**不再落回任何仓库**
- 定期轮换（`ansible-vault rekey` 可在不触碰加密内容的前提下更换密码）
- 在 CI/CD 平台中设为 masked secret，确保日志不暴露

#### 方案二：外部密钥管理服务（HCP Vault / AWS Secrets Manager）

适合大型团队或已有 KM 基础设施的场景：

```yaml
# 从 HashiCorp Vault 读取密钥
- name: 获取数据库密码
  community.hashi_vault.vault_read:
    url: https://vault.example.com
    path: secret/data/myapp
    token: "{{ vault_token }}"
  delegate_to: localhost
  run_once: true
  register: db_secret

- name: 写入应用配置
  template:
    src: myapp.conf.j2
    dest: /etc/myapp/config.conf
  vars:
    db_password: "{{ db_secret.data.data.db_password }}"
```

```yaml
# 从 AWS Secrets Manager 读取（需 AWS 凭证）
- name: 获取 GPU 集群的 SSH 密钥
  community.aws.secretsmanager_secret:
    name: gpu-cluster/ssh-key
    state: present
  delegate_to: localhost
  register: ssh_secret

- name: 写入 SSH 私钥
  copy:
    content: "{{ ssh_secret.secret_value }}"
    dest: /home/ubuntu/.ssh/id_rsa
    mode: '0600'
    owner: ubuntu
```

#### 方案三：CI/CD 环境变量注入（最安全）

在 CI/CD 管道中设置环境变量，通过 `lookup('env', ...)` 读取，密钥全程不进仓库：

```yaml
# playbook.yml
- name: 配置 Docker 仓库认证
  docker_login:
    registry: "{{ lookup('env', 'DOCKER_REGISTRY') }}"
    username: "{{ lookup('env', 'DOCKER_USERNAME') }}"
    password: "{{ lookup('env', 'DOCKER_PASSWORD') }}"
  no_log: true  # ← 关键：防止 Ansible 将敏感值输出到日志
```

```yaml
# GitHub Actions 中调用
- name: Deploy with Ansible
  run: |
    ansible-playbook deploy.yml \
      -e "API_KEY=${{ secrets.API_KEY }}" \
      -e "DB_PASSWORD=${{ secrets.DB_PASSWORD }}"
  env:
    ANSIBLE_HOST_KEY_CHECKING: "false"
```

配合 `--extra-vars` 从外部传入，playbook 内用 `no_log: true` 保护敏感值。

#### 安全规范要点

```yaml
- name: 任何涉及密钥的任务
  shell: some-sensitive-command
  no_log: true                # 防止 stdout/stderr 泄露
  changed_when: false         # 敏感操作不暴露变更状态
  delegate_to: localhost      # 尽量在控制节点完成密钥操作
```

- 密钥文件和 playbook 可以进同一仓库（Vault 加密），也可以分仓库管理（推荐）
- Vault 密码本身是唯一的"真实密钥"，单独保存在密码管理器或 CI/CD secrets 中
- 所有含敏感变量的模板在 `template` 模块中加 `no_log: true`
- 密钥生命周期管理：定期轮换用 `ansible-vault rekey`

### 服务开关与特性管理

#### 系统服务启停

```yaml
# 精准控制服务的运行状态
- name: NVIDIA 持久化服务

    name: nvidia-persistenced
    state: started
    enabled: true
    daemon_reload: true

- name: 按环境关闭不需要的服务
  service:
    name: "{{ item }}"
    state: stopped
    enabled: false
  loop:
    - bluetooth
    - cups
    - avahi-daemon
  when: environment == "production"
```

#### 条件化特性部署

用变量控制一组机器的行为，变量来自 inventory、group_vars 或外部 CMDB：

```yaml
# group_vars/gpu_servers/vars.yml
gpu_support: true
experimental_features: false
log_level: INFO
monitoring_agent: true

# group_vars/dev_workstations/vars.yml  
gpu_support: false
experimental_features: true
log_level: DEBUG
monitoring_agent: false
```

Playbook 根据变量自动调整行为：

```yaml
- name: 安装 GPU 相关组件
  when: gpu_support | default(false)
  block:
    - name: 安装 NVIDIA Container Toolkit
      apt:
        name: nvidia-container-toolkit
        state: present
    - name: 配置 Docker GPU runtime
      template:
        src: daemon.json.j2
        dest: /etc/docker/daemon.json
      notify: restart docker

- name: 配置实验性特性
  when: experimental_features | default(false)
  template:
    src: experimental.conf.j2
    dest: /etc/myapp/features.d/experimental.conf
```

#### 模板驱动的配置开关

Jinja2 模板将变量映射为配置文件中的开关：

```jinja2
{# /etc/ssh/sshd_config.d/gpu-cluster.conf.j2 #}
{# 仅 GPU 集群节点启用特定 SSH 配置 #}
{% if gpu_cluster | default(false) %}
TCPKeepAlive yes
ClientAliveInterval {{ ssh_alive_interval | default(60) }}
ClientAliveCountMax {{ ssh_alive_count | default(3) }}
{% endif %}

{# 端口转发开关 #}
{% if allow_tunnel | default(false) %}
AllowTcpForwarding yes
GatewayPorts clientspecified
{% else %}
AllowTcpForwarding no
{% endif %}
```

#### Handlers：变更触发动作的核心模式

这是 Ansible 最实用的模式之一——**配置变了才重启，没变不动**：

```yaml
---
- name: 配置 Docker 守护进程
  hosts: gpu_servers
  vars:
    gpu_servers:
      - server1
      - server2

  tasks:
    - name: 写入 Docker daemon 配置
      template:
        src: daemon.json.j2
        dest: /etc/docker/daemon.json
      notify: restart docker           # ← 只在该任务产生变更时才触发
      vars:
        default_runtime: "{{ 'nvidia' if gpu_enabled else 'runc' }}"

    - name: 写入 NCCL 配置
      template:
        src: nccl.conf.j2
        dest: /etc/nccl.conf
      notify: reload nccl config

    - name: 拉取最新训练镜像
      docker_image:
        name: "{{ training_image }}"
        source: pull
      notify: restart training container

  handlers:                            # ← 被 notify 触发的动作
    - name: restart docker
      systemd:
        name: docker
        state: restarted
        daemon_reload: true

    - name: reload nccl config
      debug:
        msg: "NCCL config updated, next training run will pick it up"
```

**为什么重要**：避免无意义的服务重启。Docker daemon 重启会干掉所有运行中的容器，只有 daemon.json 确实变了才触发。

#### Inventory 驱动的配置差异

不需要写多个 playbook，同一个 playbook 对不同组执行不同操作：

```yaml
# inventory.yml
all:
  children:
    gpu_cluster:
      hosts:
        gpu-01:
          nvidia_driver_version: "550"
          gpu_count: 8
        gpu-02:
          nvidia_driver_version: "550"
          gpu_count: 8
    dev_workstations:
      hosts:
        dev-mac-01:
          ansible_connection: local
        dev-linux-01:
          gpu_count: 1
```

```yaml
- name: 按机器配置调整 NCCL 参数
  template:
    src: nccl.conf.j2
    dest: /etc/nccl.conf
  vars:
    nccl_tuning: "{{ 'gpu_cluster' if group_names == 'gpu_cluster' else 'single_gpu' }}"
```

#### ansible-pull：开发机和端侧的首选模式

对于无法通过 SSH 回连控制节点的场景（开发机、NAT 后的端侧设备），使用 **ansible-pull** 反转模型：

```bash
# 机器定时从 Git 拉取配置并 apply
ansible-pull -U https://github.com/team/machine-config.git \
  -i localhost, \
  playbooks/workstation.yml \
  --accept-host-key
```

用 systemd timer 定期执行：

```ini
# /etc/systemd/system/ansible-pull.service
[Unit]
Description=Ansible Pull定期同步

[Service]
Type=oneshot
ExecStart=/usr/bin/ansible-pull \
  -U https://github.com/team/machine-config.git \
  -i localhost, \
  playbooks/workstation.yml
Nice=19
```

```ini
# /etc/systemd/system/ansible-pull.timer
[Unit]
Description=每6小时同步一次机器配置

[Timer]
OnCalendar=*-*-* 0,6,12,18:00:00
RandomizedDelaySec=1800

[Install]
WantedBy=timers.target
```

这样开发机和端侧设备就会定期"打电话回家"拉取最新配置，控制节点不需要知道它们在哪。适合 macOS 开发机（用 Homebrew 装 ansible 后设为 launchd 定时任务）和 Jetson/树莓派等端侧设备。

### AI Infra 中的快变层示例

| 配置项 | 变更频率 | 管理方式 | 说明 |
|--------|---------|---------|------|
| NVIDIA 驱动版本 | 季度 | Packer 固话 | 需要重启，适合随镜像更新 |
| Docker daemon.json | 月级 | Ansible template + handler | 改 runtime/registry 配置，handler 安全重启 |
| NCCL 环境变量 | 周级 | Ansible template | 调参频繁，不适合固化到镜像 |
| SSH 密钥 | 不定 | Ansible + Vault | 人员变动时通过 playbook 注入/撤销 |
| 实验性特性开关 | 天级 | Ansible vars + template | 由 group_vars 或 CMDB 控制 |
| 监控 agent 配置 | 周级 | Ansible template + handler | 新指标/告警通道变更 |
| 容器镜像版本 | 每次 | Docker / Ansible | Ansible 拉取并重启容器 |
